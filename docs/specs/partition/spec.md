# Partition — durable specification

> **Bounded context:** `partition` (the package itself).

## Business objective

Partition packages one method as an APM package: the **living specification** and the **Context Budget**. A project installs it, gets the skills, and the method is updated in one place.

The name carries both halves. A _partition_ is the score the musicians perform: the specification the code implements. It is also the split of a system into bounded contexts the assistant can hold in full.

Partition does not orchestrate. It has no workflow engine, no role agents and no ceremony. It bounds the work and makes it last, beside whatever drives the process.

## Scope

**In scope:** the durable spec of a bounded context, the area file shared by the bounded contexts of one area, and the register of project-wide invariants; the plan as the state of the work, and its closing; the measure of the Context Budget; the shape of a new bounded context from a source (an API contract, a PRD, a spec written before Partition, a described context), and the reshape of existing ones after a workshop (fission, merge, removal, move) or the promotion of a component; the architecture as a C4 text model, and the transformation of an existing `.drawio` file into that model; the form of a hexagon; the project's rulings on patterns; the project's rule files and their scope; the audit of a change before it ships; the README kept in step with the code.

**Out of scope:**

- Process orchestration: brainstorming, sprint planning, the TDD loop, code review. A process tool does that, for example Superpowers, on Claude Code and on GitHub Copilot CLI.
- Skills for one language, framework or vendor. They may become packages of their own; they never enter this one.
- Rule content. The package ships the skeletons of two profiles, backend and frontend, as questions.
- Deciding where a boundary goes, what a business rule says, or whether a change ships without evidence.
- MCP servers, and any primitive that runs without being asked.

## Language

The vocabulary of the package is explained once, in the [glossary](../../../.apm/skills/partition-spec/references/glossary.md). One meaning per term; a synonym is read, never written.

## Business rules

Each rule says how it is verified. The expected result is written before the command runs.

### The package

| # | Rule | Verification |
| --- | --- | --- |
| BR-1 | An update never touches an instance. | Install, edit every instance, install again: `git status` shows no change. |
| BR-2 | The package keeps its own budget: the always-loaded surface (instruction, skill and agent descriptions) stays under 2 000 tokens, each `SKILL.md` under 3 000. | `npm test`; `budget.mjs --package .` |
| BR-3 | No `SKILL.md` names a language, a framework or a vendor of the project under work; per-ecosystem material lives under `references/`. | `npm test` |
| BR-4 | Nothing runs unasked and nothing needs installing: no hook primitive, no MCP server, no dependency in what the package ships; a script is one file for Node 22 or later, the Python standard library or Bash, and runs only when a skill says so. The repository's own tooling may take a `devDependency` when nothing built into Node does the job, locked by `package-lock.json`. | `npm test` |
| BR-5 | Every primitive deploys on `claude` and on `copilot`, at the consumer's choice. | `apm install <package> --target claude,copilot` in a trial project |
| BR-6 | The instruction is in context when a session starts: it carries no file scope. | `npm test`; the deployed files; then a fresh session on each target |
| BR-7 | A file shipped as a template is never deployed as a primitive. | `npm test`; the count of instructions `apm install` reports |
| BR-8 | Everything is in English, and nothing names a client or an employer. | Read by the owner before each commit. |
| BR-28 | The instruction names the skill of each step the method requires without the user asking for it: `partition-spec` when a behaviour changes or code and spec disagree, `partition-plan` for the state of the work, `partition-shape` for a source, `partition-gate` and `partition-readme` at closing. Every other skill is found by its description. | `npm test` |
| BR-32 | A file deployed as an instruction has no `#` or `##` heading: its sections start at `###`, and its name is in its `description`. `apm compile` gives `AGENTS.md` its level-1 heading and each instruction its own level-2 heading. The package's instruction and the rule skeletons follow it; `partition-rules` gives a migrated rule that form, changing its headings only. | `npm test`; `apm compile` in a trial project |
| BR-34 | The package's Markdown is formatted with Prettier `proseWrap: "never"`, so a wide table is not padded. Each field stays on its own line under any prose wrap: the lines of a header blockquote (a plan's `Status`, `Resume at`, `Last updated`; a spec's `Source` to `Decomposition`; a decomposition record's `Provenance`) are separated by an empty `>` line, and the fields of a plan task or of a reshape proof are list items. A script reads them line by line. | `npm test`; `npm run format:check` |

### The method the skills enforce

| # | Rule | Enforced by |

| BR-9 | One durable spec per bounded context, in which a concept has one meaning and no synonym. A word given two meanings in one bounded context is not written: the assistant asks which meaning holds there and whether the other belongs to another bounded context, recalls that a word meaning something else in a neighbour marks a boundary, and records the question in `Open questions` until a person settles it. An entry of `Open questions`, this question or one a source leaves unsettled (BR-10), leaves it once a person settles it, in the change that writes the answer, that answer being the owner's word for its removal; an entry no person has settled is removed only by the owner (proposed, run s20d-1). A statement of how code is written is a line of a rule file, scoped to the code it binds (BR-23), never a business rule or an area rule, however many bounded contexts it reaches (proposed, run s16a2-1). | BR-10 | The spec moves first: a gap between code and spec is settled in the spec before the code changes. The assistant says which side is wrong and why, and asks when it cannot tell. | BR-11 | Plans keep no decision log outside themselves. A durable statement a plan establishes goes to the spec of its bounded context, to the area file of its area, or to the invariant register if it passes the admission test; the dated reason stays in the plan that produced it. The `Decisions` section of a durable spec holds only the decisions its source states, each with its reason, its anchor and its date. A ruling of the source that states a rule and gives its reason goes to both places: the rule to `Business rules`, marked "from source" under the "TO VALIDATE" banner (BR-13), the choice with its reason to `Decisions`, each anchored to the same ruling. A statement of the source that records a choice without its reason is not one of these decisions: it is pointed to, and asked as an open question only when it leaves something unsettled (BR-19, BR-26); the date of a decision is the version or date of its source (BR-26) (proposed, run r08-4c2-2). | `partition-plan`, `partition-spec`, `partition-shape` |
| BR-12 | The admission test has three conditions, all required: true for every feature; spanning at least two areas or layers; a defect when violated. A layer is a ring of a hexagon; a statement spans layers when it binds the same layers in every hexagon of the project. Most plans admit nothing. | `partition-spec` |
| BR-29 | A statement lives at the lowest level that holds it all: the durable spec of one bounded context, the area file of one area, the invariant register for what spans areas or layers. A lower level never contradicts a higher one: a contradiction stops the work and goes to the owner, and it is never settled by editing the higher level. A rule a request contradicts is reversed as any behaviour changes: a rule copied from a source through its source (BR-10); a rule a person wrote through `partition-spec`, validated by the owner. A statement is placed against what the other areas already hold: one that the area file or a spec of another area also holds spans two areas, so it goes to the admission test, not to an area file, and the file and identifier that hold it are reported, nothing moved (proposed, run r08-4c-1). | instruction, `partition-spec` |
| BR-13 | A business rule, an area rule or an invariant is never deduced from a source, a field name, an example or code. A rule a source states is copied word for word, marked "from source" with its anchor. The section stays under a banner, "TO FILL" while empty and "TO VALIDATE" while it holds only copied rules, until a person confirms it; a bounded context under banner is not fit for design. A copied invariant enters the register only through the admission test; one that fails it becomes an area rule or a business rule, at the level that holds it. No entry is written to the register or to an area file before the owner validates it. When a new bounded context enters an area that has an area file, each area rule already in the area file is proposed to bind it or not, with the reason; its `Binds` changes only once the owner agrees. An entry copied from a source keeps its anchor and is never rewritten: a change of the source is reported. A statement the source makes outside any unit is anchored by its place in the source, in the form the reader of that source gives, and its anchor is written whole, the same way, wherever the entry is copied or quoted (proposed, run r08-5e-2). A sentence of the source that replaces a copied one is a change of that rule, reported with its new wording, never a rule added beside it. | `partition-spec`, `partition-shape` |
| BR-14 | The plan is the only state, and it is read in part: header, task index, the task named in `Resume at`, and `Blockers`, whose carried entries every turn checks (BR-15) (proposed, run s20a-1). A `done` plan is not read. A decision that binds a later task is written, when it is recorded in `Decisions`, into the section of each task it binds, so that the part read holds everything the task needs from the plan (proposed, run s04d-2). | instruction, `partition-plan` |
| BR-25 | The folder of the plans is declared once in `docs/partition.yml`. `paths.plans` decides it, even with `bridge: superpowers`, which only says the Superpowers plugin writes the plan's body. When nothing is declared there, an instruction of the project that names one folder settles it: the assistant uses and records it, and says so when the user's own instructions name another. Without one, it looks in the two known folders; one found, it uses and records it; none or several, it asks once and records the answer. | instruction, `partition-plan` |
| BR-31 | `docs/partition.yml` follows the schema `partition-budget` ships, `assets/partition.schema.json`, the only list of its keys; the template's first line points the editor at the schema beside it, and the skill that creates `docs/partition.yml` rewrites it to the installed copy, as the template's second line says. Filled from the template, it keeps every key the owner's answers leave alone, at its value and with its comment; only the example bounded context goes. No bounded context is asked when the file is created: `contexts:` stays empty until `partition-shape` declares each bounded context it retains, or `partition-reshape` a fission's (BR-26). `budget.mjs` checks the file before it measures: an unknown key, a wrong type, a value outside its list or its range or a bounded context without `id` stops it with every finding and its path, exit 2. A key without a value counts as absent. | `partition-budget`, `budget.mjs`, `npm test` |
| BR-15 | Done means the real output of the verification command, next to the expected result. A verdict is earned by execution; what could not run caps it. A blocker that says a file, a line or the result of a command of the repository is not yet as required is such a verdict, on a state the plan read in part does not hold (BR-14): it is written only after the assistant has read that file or run that command in the turn that writes it; when the repository already shows it done, no blocker is written, and an entry carried from an earlier turn is deleted (proposed, run r08-6g-2). | instruction, `partition-gate`, `partition-plan` |
| BR-16 | The budget is measured by one gauge per bounded context, against a threshold set per project (32 000 by default): what any task of it loads before reading code, that is every session, the invariant register, the area file of its area, its spec and the scoped rules that match its code. Every assessment is recorded by date: one record per day, `docs/budget/YYYY-MM-DD.md`, which a second assessment the same day replaces and no later day overwrites. | `partition-budget` |
| BR-17 | Partition never decides a boundary. It measures, prepares, proposes or challenges when the architect asks, and records; the record names the people who decided. | `partition-budget`, `partition-reshape` |
| BR-18 | A neighbour is seen through its contract only. | instruction, `partition-attack` |
| BR-19 | A source is split by the six criteria C1–C6 and the six rules R1–R6, defined once and applied to its units. A unit is an operation of an API contract, or a requirement or story of a document, or one of its sections when the document identifies none; a part that only records decisions, defines terms or gives context is not a unit: the decisions it states are copied, the rest is pointed to. A strong sharing of data or of business rules argues against a split; a rule found in two specs of one area is reported, never moved by the assistant, and a rule a spec of another area already holds is reported too, as a candidate for the admission test (BR-29); when it fails it, a person names its owner, then `partition-spec` writes it into that owner's `Business rules`. Nothing is written before the owner validates the plan; a new bounded context, a merge, a removal, a move and a scope extension are validated by name. Every new bounded context outside a reshape is created by `partition-shape` from a source, a described context included, never started by `partition-spec`; the one a fission creates is `partition-reshape`'s (BR-30). A specification written before Partition is a source like any other: read where it lives (BR-26), decomposed by `partition-shape`, never taken over as is; its rulings are read as the decisions and rules it states. The contract of a system the repository only calls is read where it lives, recorded in `Contracts with neighbours` of the bounded context that calls it, and never decomposed; an API contract given for a bounded context that exists, whose decomposition records another source, is not a source of that decomposition: it is the contract that bounded context shows (BR-18), recorded in its `Contracts with neighbours`; the recorded source stays the only source of the decomposition, its provenance unchanged, and no shaping procedure is entered for it; a contract given to shape bounded contexts that do not exist yet is a source (proposed, run s20c-2). A change of a source is classified before it is routed: breaking when it withdraws or tightens what was asked (a unit of the scope removed or renamed included), additive when it only adds, neutral when only its wording changes; a breaking change is reported loudly and the code searched for it (proposed, run r07-2). | `partition-shape`, `partition-spec` |
| BR-20 | The text model is the source of the C4. Regenerating never moves what a person positioned, but one box: of two kept boxes of a page that overlap, the later in the model's order takes a free place as a new box would, and the run names it (proposed, owner, 2026-10-16). What the generator placed and no person changed since is the generator's: each run places, frames and routes it again from the model, so that a page never keeps the layout of elements that left it; the generator tells it from a person's by a mark it writes on each cell it places (proposed, owner, 2026-10-17). What the generator places overlaps no box and no boundary it is not inside, and a boundary encloses its children: a kept boundary only grows to hold them. No edge it routes crosses a box other than its ends, and two relations between the same boxes run on tracks of their own; no two relations it routes share a stretch of line, when the page leaves room for that (proposed, owner, 2026-10-17). | BR-24 | A README is derived: realigning it changes neither code nor spec. | `partition-readme` |
| BR-26 | A spec derived from a source points to it: the units it owns, each linked by its anchor or operationId. The bounded contexts a decomposition creates are declared in `docs/partition.yml` with their area. A persistence mapping is not a copy: it says where the data of the bounded context is stored, which the source does not hold, and names a field of the source only to place it. A merge carries the hand-written sections of both specs over by a person, and brings down to the merged spec the area rules only its two halves shared. After a merge, a removal or a move, an area rule that binds, or a word of the area file that only one bounded context uses, comes down to that bounded context's spec, carried by a person; an area file left with no entry is deleted by a person, and its area loads none (proposed, review of 2026-10-17). A removal deletes nothing before the owner rules on it. A bounded context a merge absorbed or a removal ended stays declared in `docs/partition.yml` with its area (BR-26) as long as its spec folder exists, and is taken out once a person has deleted that folder (proposed, run s13b5-1). Where the boundary goes is reached as BR-33 says. A reshape record is read by the architect at the next boundary decision, and by `partition-budget` at the scheduled assessment, to explain a gauge. | `partition-reshape`, `partition-budget` |
| BR-33 | Before a boundary moves (the decomposition of a source, a new bounded context, a fission, a merge, a removal or a move; not an attachment, not a promotion), the assistant tells the architect the decision is theirs and lets them choose how to reach it: a workshop, whose result comes back in any readable form and is saved under `paths.sources`, or a proposal of two or three options, numbered, each with the criteria it satisfies, what it costs and what it brings, one of them recommended. The recommended option is one the criteria C1–C6 and the rules R1–R6 leave (BR-19); an option that keeps a point against a criterion may be shown, naming the criterion it breaks, never recommended: keeping it is the architect's decision (proposed, run r08-2b-1). When the criteria leave a single split, it is said with why the others fall. A workshop result is challenged against the source, the criteria, the material prepared and the invariant register; each bounded context the result names is checked against R1 from the source alone, and one that fails it is a finding, whatever the result decides: improvements are proposed, or it is taken as it is. The architect decides. In a proposal, each new bounded context carries the assistant's name for it, from the naming rule of the criteria; the architect keeps it or chooses another when deciding the boundary. A point kept against a criterion is recorded with the criterion, the names, the date and the reason, and is not proposed again unless a later delta changes, for its units, the criterion it was kept against. | `partition-shape`, `partition-reshape` |
| BR-27 | Ticking the last task of a plan starts its closing in the same turn, without waiting to be asked. A plan closes only after a `partition-gate` verdict on its changes. HOLD keeps it `in progress`. Each reason of a HOLD and each condition of SHIP WITH CONDITIONS becomes a task when the assistant can meet it, a blocker with its owner when only a person can. At closing, every statement the work established goes to its level (BR-29), a statement already written into a spec during the work included: its level is checked then, and the candidates rejected are reported. When what users install, run or configure changed, the README is realigned before the plan is `done`. At closing, every task still marked `uncommitted` carries its date alone: it lands in the closing commit, which `git log -1 -- <plan>` finds. | instruction, `partition-plan` |

## Where not to give in

- **One more skill.** Each one costs every session of every project. A skill enters by replacing another, or by a decision recorded in the plan. BR-2 does not move to make room.
- **Project rules as defaults.** The day the package ships an architecture rule, every project inherits someone else's architecture.
- **A decision left in the chat.** It did not happen.
- **A business rule written by the assistant.** It reads well and nobody ruled it. Copying one a source states is not writing it; confirming it is still a person's act.
- **A source copied into a spec.** The copy drifts from the source the day the source moves.
- **An explanation given twice.** The two drift apart. A term, a rule or a procedure is explained in one place; everywhere else it is named, with a pointer.
- **Auto-layout over hand layout.** One regeneration that scrambles a diagram and the model stops being the source.
- **A budget without a number.** It becomes an opinion held in a meeting.
